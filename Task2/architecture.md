# Отчёты о работе протезов BionicPRO

Пилот получает дневные показатели каждого своего протеза: число измерений,
движений и ошибок, средний и максимальный отклик, минимальный заряд батареи.
Отчёт доступен в личном кабинете и скачивается в JSON. Распознавание движений
по-прежнему работает на чипе; подготовка отчётности не участвует в управлении
протезом и не влияет на требование отклика до 100 мс.

[Диаграмма контейнеров draw.io](bionicpro-reports.drawio) и
[её PNG](bionicpro-reports.png) показывают один региональный контур.
Схема развивает [архитектуру доступа](../Task1/architecture.md).
Новые компоненты отчётности выделены зелёным, компоненты доступа — синим,
исходные внешние системы — серым. Сплошные связи реализованы в стенде;
пунктир показывает будущие подключения к исходным бизнес-системам.

## Компоненты и источники

CRM — система управления отношениями с клиентами. API — программный интерфейс
для запросов приложений. BFF (backend for frontend) — серверная часть,
обслуживающая браузер и обращающаяся к другим сервисам от его имени.
UTC — единое время, по которому определяются границы дней в отчёте.

- `reports-api` на Go реализует часть исходного API, отвечающую за отчётность.
  Он проверяет access-токен Keycloak и читает готовые строки из ClickHouse.
- `bionicpro-auth` проверяет серверную сессию, при необходимости обновляет
  access-токен и передаёт его API. Браузер работает только с HttpOnly/Secure cookie.
- Apache Airflow запускает ETL — извлечение, преобразование и загрузку данных —
  и публикует витрину: таблицу готовых показателей для быстрого чтения API.
- PostgreSQL CRM содержит клиентов, модели протезов и интервалы владения.
  Отдельный PostgreSQL телеметрии содержит события работы протезов.
- ClickHouse — OLAP-база, предназначенная для аналитических чтений. В ней
  хранятся витрина `report_mart` и реестр готовых дней `report_periods`.
- Отдельный PostgreSQL Airflow хранит расписание и состояния задач; это
  служебная БД, через которую API не получает медицинские данные.

Код исходных CRM/Битрикс24 и приёма телеметрии не предоставлен. Поэтому стенд
реализует их контракты двумя учебными БД, а не имитирует готовую интеграцию
с реальным Битрикс24. Скрипт `seed_demo.py` создаёт только синтетические данные.
Он находит действительные ID `user1` и `user2` в локальном Keycloak и сохраняет
их в CRM. Имя пользователя не служит основанием для доступа к отчётам.

Все источники, Airflow, ClickHouse, журналы и резервные копии должны размещаться
в стране обслуживания пользователя. Межрегиональная выгрузка отсутствует.
Телеметрия не копируется в БД Keycloak или профилей Яндекса.

## Контракт источников

[CRM](../sources/crm.sql) связывает `customer_id` с неизменяемым `keycloak_subject`
из проверенного токена. Таблица `ownership` хранит интервалы владения протезом
`[valid_from, valid_to)`, то есть включая начало и исключая конец.
Ограничение PostgreSQL запрещает пересекающиеся интервалы одного протеза.
При передаче протеза события распределяются по владельцу на момент события.
Исторические показатели прежнего владельца остаются доступными только ему.

[Телеметрия](../sources/telemetry.sql) содержит уникальный `event_id`, ID протеза,
время измерения, число движений за это измерение, отклик в миллисекундах, заряд
в процентах и признак ошибки. Движения считаются приращением, а не накопительным
счётчиком. Одна строка означает одно измерение. Средний отклик рассчитывается
по всем измерениям, в том числе с признаком ошибки; сырые миосигналы в отчёт
не входят. Перед подключением реальных датчиков этот контракт нужно подтвердить.

Оба источника содержат `export_checkpoint.closed_through`: время, до которого
они считают данные закрытыми для выгрузки. Отсутствие событий не доказывает
готовность дня. Контрольная отметка должна охватывать весь интервал, включая
дни без телеметрии. В стенде её выставляет скрипт заполнения; в рабочей системе
это обязанность CRM и процесса приёма телеметрии.

## Расписание и публикация

[DAG `bionicpro_reports`](../airflow/dags/report_etl.py) — граф зависимых задач.
Он выполняется раз в сутки
после 00:00 UTC (03:00 Москвы) за предыдущий завершённый день.
Airflow передаёт `data_interval_start` и `data_interval_end`; эти границы
определяют выгрузку, а не текущее время запуска. `catchup=False` отключает
автоматическую выгрузку всей истории с начальной даты. Пропущенные дни
обрабатываются явно через backfill. В каждый момент активен один запуск;
каждая задача допускает две повторные попытки с интервалом в минуту.

1. `build_mart` проверяет закрытие дня в обоих источниках. Каждая БД читается
   в собственной транзакции с неизменным снимком и запретом записи.
2. CRM передаёт интервалы владения и модель протеза. Телеметрия читается
   потоковым курсором по границам дня. ETL объединяет записи по ID протеза
   и времени владения и рассчитывает показатели по клиенту и протезу.
3. Протез без событий получает строку с нулевыми счётчиками и `null` для
   отклика/заряда. Событие без однозначного владельца останавливает подготовку;
   данные не теряются молча и не попадают чужому пользователю.
4. Витрина записывается порциями до 10 000 строк с новым `batch_id` — UUID
   версии. Версия после загрузки не изменяется. Запись выполняется синхронно.
5. `publish` проверяет фактическое число записанных строк и только затем
   добавляет запись готовности дня. Метаданные между задачами передаются
   через XCom Airflow: только день, ID версии и число строк.

Сбой до публикации оставляет невидимую API версию. Повторная подготовка создаёт
новую версию; реестр выбирает последнюю опубликованную. Повтор задачи публикации
может добавить служебную запись, но не удваивает пользовательские показатели.
Предыдущая успешная версия остаётся доступной во время повторной загрузки.

Позднее событие или исправление CRM требует повторной обработки затронутого
дня. Это ежедневная витрина, а не отчёт реального времени. Готовность означает
полноту относительно предоставленных снимков и контрольных отметок источников.

## Структура витрины и чтение

Ключ одной логической строки: `(subject, day, prosthesis_id)`.
Физически строка дополнительно содержит `batch_id`, чтобы разные версии
не смешивались. ФИО, email и другие атрибуты профиля в витрину не копируются.

| Поля | Назначение |
| --- | --- |
| `subject`, `day`, `prosthesis_id`, `model` | Пользователь, день UTC, протез и модель |
| `samples`, `movements`, `errors` | Счётчики измерений, движений и измерений с ошибкой |
| `avg_response_ms`, `max_response_ms`, `min_battery_pct` | Подготовленные метрики; `null`, если измерений нет |
| `batch_id` | Неизменяемая версия подготовки |

[DDL ClickHouse](../clickhouse/init.sql) использует MergeTree с сортировкой
`(subject, day, prosthesis_id, batch_id)`, чтобы чтение начиналось с нужного
пользователя и периода. Разделы таблицы создаются по месяцам. Реестр дней
использует ReplacingMergeTree с номером публикации; API читает его с `FINAL`,
чтобы выбрать последнюю запись до фонового объединения служебных строк.

API сначала получает опубликованные версии **каждого** дня периода, затем
читает витрину с фильтром по `subject` и ровно этим версиям. Таким образом,
публикация между двумя запросами не меняет выбранный набор данных. На запросе
пользователя нет соединения с CRM, расчёта метрик или чтения сырой телеметрии.
Сортировка готовых строк и чтение малого реестра выполняются в ClickHouse.

## API и доступ

Публичные адреса `GET /reports` и `GET /api/reports` идут через BFF на
внутренний `GET /reports` Go-сервиса. Параметры: `from` и `to` в формате
`YYYY-MM-DD`, UTC, начало включается, конец исключается; максимум 31 день.
Например: `/api/reports?from=2026-09-28&to=2026-10-01` возвращает 28–30 сентября.

| Код | Поведение |
| --- | --- |
| 200 | JSON: границы, UTC, опубликованные версии, строки своих протезов |
| 400 | Неверные даты, длинный период, повтор параметра или переданный `user_id`/`subject` |
| 401 | Нет действующей сессии либо access-токен не прошёл проверку API |
| 409 | Хотя бы один день не опубликован; `missing_days` перечисляет отсутствующие дни |
| 503 | ClickHouse временно недоступен; через BFF сетевой сбой также может дать 502 |

Пользователь без протезов получает пустой `rows`, если весь период подготовлен.
Сервис не подменяет недоступные данные нулями и не обрезает запрошенный период.
Ограничение результата — 10 000 строк; превышение завершается ошибкой, а не
незаметным усечением отчёта.

JWT — подписанный токен с данными о пользователе и сроке доступа.
JWKS — набор открытых ключей для проверки этой подписи. Go-сервис
самостоятельно проверяет подпись RS256 через ключи Keycloak,
издателя, аудиторию `reports-api`, срок действия, время выпуска, наличие `sub`
и клиента `azp=bionicpro-auth`. `subject` для SQL берётся только из токена.
Даты, `subject` и UUID версий передаются типизированными параметрами ClickHouse.
Роль администратора не даёт права читать чужие отчёты через этот эндпоинт.
Заголовки пользователя с произвольным ID не участвуют в проверке прав.

Сервис не публикует порт на хосте. К сети `reports` подключены BFF и Go API;
Nginx не проксирует запросы непосредственно в Go. Аккаунт ClickHouse
`reports_api` ограничен чтением БД `reporting`. У API нет паролей CRM,
телеметрии или администратора Keycloak. Ответы имеют `Cache-Control: no-store`.
Токены IdP и служебные заголовки не передаются браузеру.

Лимиты чтения задаются в серверном профиле ClickHouse: 8 секунд на запрос,
256 МиБ памяти и 10 000 строк результата. API не изменяет настройки
аккаунта в режиме только чтения.

## Ограничения и дальнейшие решения

- **Учебные источники:** подключения к Битрикс24 и производственному API
  телеметрии отсутствуют. Нужно реализовать адаптеры и процесс выставления
  контрольных отметок. Независимые снимки двух БД не дают общей транзакции;
  при несогласованной истории владельцев DAG отказывает в публикации.
- **Нагрузка ETL:** ежедневное потоковое чтение сокращает память для событий,
  но всё равно нагружает транзакционную БД. Словарь владения и готовые строки
  находятся в памяти рабочего процесса. Объём промышленного дня неизвестен;
  нужны нагрузочные измерения и затем реплика для чтения либо CDC из задания 4.
- **Версии:** старые и незавершённые версии сохраняются, чтобы API мог закончить
  чтение выбранного набора. Политика очистки и срок хранения требуют отдельного
  решения. Удаление должно учитывать выполняющиеся запросы и резервные копии.
- **Отзыв доступа:** удаление учётной записи закрывает вход, но пользовательские
  отчёты остаются в ClickHouse. Процесс удаления по запросу и немедленного
  отзыва токенов требует реализации. Задержка отзыва токена до 120 секунд
  наследуется от задания 1; изменение ID при пересоздании аккаунта требует
  подтверждённой перепривязки CRM.
- **Эксплуатация:** внутренние SQL/HTTP в Docker не шифруются; изоляция сетей
  предназначена для локального стенда. Нужны внутренний TLS, секрет-хранилище,
  резервирование, ограниченные учётные записи ETL, аудит и мониторинг свежести.
  Airflow 2.10.5 выбран для воспроизводимого учебного DAG; перед промышленным
  запуском нужно обновить и проверить зависимости и образы.
- **Клиенты:** реализован предоставленный React-интерфейс. Исходников
  нативного Android-приложения в репозитории нет; API подготовлен для его
  последующей интеграции с соответствующей моделью безопасного входа.
