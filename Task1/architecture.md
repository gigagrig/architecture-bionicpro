# Управление доступом BionicPRO

Система объединяет вход в личный кабинет и проверку пользователей региональных
представительств. Персональные данные и телеметрия протезов остаются в стране
обслуживания. Распознавание миосигналов выполняется на чипе протеза и не зависит
от доступности службы входа.

Исходные компоненты показаны в [BionicProC4.png](../BionicProC4.png).
Обновлённая [диаграмма draw.io](bionicpro-security.drawio) содержит две страницы:
контейнеры системы и региональные контуры. [PNG контейнеров](bionicpro-security.png)
и [PNG регионов](bionicpro-regions.png) доступны без редактора. Зелёным отмечены новые компоненты,
синим — исходные. Пунктирные связи обозначают предлагаемую дальнейшую интеграцию.

## Региональные контуры и источники учётных записей

Каждое представительство использует собственные Keycloak, `bionicpro-auth`,
каталог пользователей, CRM (систему работы с клиентами), базы профилей
и медицинских данных. Keycloak выступает как IdP (Identity Provider) — служба
подтверждения личности. Он подключает местный LDAP-каталог учётных записей
и внешние IdP по протоколам OpenID Connect, SAML или OAuth 2.0.
Контракт входа для приложений и названия ролей одинаковы во всех регионах.

Пользователь открывает адрес своего представительства. Регион закрепляется
при регистрации; смена адреса сайта не переносит учётную запись. Глобальная БД
пользователей не создаётся. Атрибуты LDAP, секреты одноразовых кодов, связи внешних
аккаунтов, журналы, ключи и резервные копии остаются внутри соответствующего
регионального контура. LDAP другой страны обслуживает Keycloak этой же страны,
а не центральный российский сервер. Между регионами распространяются только
код и шаблоны настройки без персональных данных.

Локальный Compose моделирует один контур. Перед реальным развёртыванием нужно
выбрать страну, провайдера, сроки хранения и условия трансграничного доступа.
Само размещение контейнеров не подтверждает соблюдение законодательства.

## Вход и серверные сессии

`bionicpro-auth` реализует backend for frontend (BFF) — серверную часть
интерфейса, которая обращается к IdP от имени браузера. Токены остаются
на сервере: access-токен даёт доступ к API (программному интерфейсу сервиса),
refresh-токен обновляет его, ID-токен подтверждает вход.
React получает только сессионную cookie.

1. На `/auth/login` BFF создаёт `state`, `nonce`, `code_verifier` и хранит их
   пять минут. Одноразовая cookie связывает попытку входа с браузером.
2. Браузер переходит в Keycloak. BFF передаёт хеш `code_verifier` по схеме
   PKCE S256: перехваченного кода недостаточно для получения токенов.
   Обмен также требует секрета клиента Keycloak.
3. Keycloak проверяет пароль или ответ внешнего IdP, затем одноразовый код
   (OTP). При первом входе пользователь настраивает приложение-аутентификатор.
4. На `/auth/callback` BFF проверяет `state` и cookie, однократно обменивает
   код с `code_verifier`. Он проверяет подпись RS256, издателя, аудиторию,
   срок токенов, `azp` (клиента-получателя) и `nonce` ID-токена.
   Настройки Keycloak добавляют `sub` (ID пользователя) и аудиторию `reports-api`.
5. BFF заменяет прежнюю сессию браузера и выдаёт `__Host-bionicpro-session`
   с `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`.
   Случайный ID не содержит данных пользователя; сервер хранит его SHA-256-хеш.

`state` защищает привязку ответа к попытке входа, `nonce` — от повторного
использования ID-токена. PKCE не заменяет эти проверки и проверку прав
на конкретный протез. Причина исходной утечки неизвестна, поэтому устранение
всех её причин не подтверждено.

| Данные | Хранение | Время жизни |
| --- | --- | --- |
| Access-токен | Память процесса BFF | 120 секунд |
| Refresh-токен | Память BFF, шифрование Fernet с проверкой целостности | Ограничен сессией Keycloak |
| Сессия BFF | Память; оба токена привязаны к одной записи | 30 минут бездействия, максимум 8 часов |
| Попытка входа | Память BFF, одноразовая привязка к браузеру | 5 минут |
| Ключ шифрования | Переменная окружения из локального `.env` | Требует отдельного управления в эксплуатации |

При запросе к защищённому ресурсу BFF обновляет истекающий access-токен через
refresh-токен. Keycloak выдаёт новую пару; повторное использование старого
refresh-токена запрещено. BFF проверяет неизменность пользователя и сохраняет
обновлённые роли. Ошибка обновления закрывает локальную сессию.

Каждый обработанный защищённый запрос заменяет ID сессии; прежний ID сразу
недействителен. Проверка, обновление токенов и замена ID выполняются под общей
блокировкой, исключающей одновременную обработку. Cookie обновляется и при
обработанной ошибке внешнего сервиса, чтобы браузер сохранил текущий ID.

Браузер последовательно отправляет запросы с `credentials: include`.
Изменяющие данные запросы требуют правильного `Origin` и отдельного
`X-CSRF-Token`; этот токен защиты от межсайтовой подделки запросов не является
токеном IdP. При неверной CSRF-проверке сессия не меняется.
Ответы BFF имеют `Cache-Control: no-store`. Шлюз не записывает
query string или cookie в access-журнал.

При выходе BFF удаляет сессию, очищает cookie и завершает сессию Keycloak.
Если Keycloak недоступен, локальный выход всё равно происходит; интерфейс
сообщает, что завершение внешней сессии не подтверждено.

## LDAP и роли

Keycloak проверяет пароль непосредственно в OpenLDAP по защищённому соединению
LDAPS с проверкой сертификата. Режим `READ_ONLY` запрещает приложению менять
пароли и группы каталога. Атрибуты пользователя импортируются в региональную БД
Keycloak, где также хранятся настройки OTP. Пароли LDAP не копируются.

Правила сопоставления переводят атрибуты LDAP в поля Keycloak:
`uid → username`, `mail → email`, `cn → firstName`, `sn → lastName`.
Из групп разрешены только `user` и `prothetic_user`. Второе имя сохранено
для совместимости с исходным каталогом; эта роль включает `prosthetic_user`.
Региональные каталоги используют те же роли и не выдают административные
права автоматически.

Роль даёт возможность пользоваться функцией, но не владение всеми протезами.
Сервис, выдающий данные протеза, сопоставляет проверенный `sub` с владельцем
протеза. Значение `user_id` из запроса браузера не является основанием для доступа.

## Обязательный одноразовый пароль

Многофакторная аутентификация (MFA) использует пароль либо внешний IdP и TOTP —
одноразовый шестизначный код, меняющийся каждые 30 секунд. Код формирует
Google Authenticator или FreeOTP. В `bionic-browser` OTP имеет требование
`REQUIRED` после основной идентификации, даже при сохранённой сессии единого
входа (SSO). Для внешнего провайдера назначен отдельный `bionic-broker-otp`.
Действие `CONFIGURE_TOTP`
включено по умолчанию. Password Grant и Implicit Flow у клиента приложения
выключены, поэтому их нельзя использовать для обхода OTP.

## Яндекс ID и согласие на профиль

Java-провайдер в Keycloak подключает Яндекс ID по OAuth 2.0. Он проверяет код
Яндекса, получает профиль по HTTPS и создаёт связь по стабильному внешнему ID
с техническим именем `yandex.<id>`. Имя, фамилия и email не импортируются.
Совпадение email не объединяет аккаунты: связывание существующей записи
требует отдельного подтверждения.

После входа и OTP интерфейс отдельно спрашивает согласие сохранить профиль.
Отказ не блокирует доступ и не вызывает запрос профиля со стороны BFF.
После согласия BFF получает токен Яндекса через серверный API Keycloak,
повторно запрашивает профиль и записывает только `id`, `login`,
`first_name`, `last_name`, `default_email`. Профиль зашифрован; версия и время
согласия сохраняются вместе с ним. Пользователь может удалить эту запись.
Удаление профиля приложения не удаляет учётную запись Keycloak и не отзывает
разрешения в Яндексе: их пользователь отзывает в настройках Яндекс ID.

Внешний токен Keycloak хранит в региональной БД для серверного получения через
роль `broker/read-token`. БД и её резервные копии требуют шифрования носителей
и ограничения административного доступа. Приложение не хранит этот токен
в собственной БД и не выдаёт его браузеру.

## Ограничения и дальнейшие решения

- Память сессий рассчитана на один процесс BFF. Перезапуск завершает все его
  сессии. Общая блокировка и сетевые запросы под ней ограничивают параллелизм.
  Для нескольких экземпляров нужен региональный Redis с неделимой заменой ID,
  блокировкой на сессию, сроком хранения и шифрованием refresh-токенов.
- Строгая ротация отвергает запросы со старым ID. Очередь устраняет гонки внутри
  одной вкладки; другая вкладка или потеря ответа может потребовать повторного
  входа. Период совместного действия старого и нового ID намеренно отсутствует.
- Отключение пользователя или изменение ролей в Keycloak обнаруживается BFF
  при следующем обновлении, максимум через срок access-токена. Для немедленного
  отзыва нужны уведомления Keycloak о выходе (backchannel logout) либо
  проверка активности токена в Keycloak при каждом запросе (интроспекция).
- HTTPS и LDAPS защищены в стенде, внутренний HTTP и PostgreSQL работают в
  Docker-сетях без публикации портов. Nginx и BFF — доверенные прокси, передающие
  Keycloak `X-Forwarded-Proto: https`. В распределённой среде нужны TLS внутри
  контура, отдельные сертификаты, секрет-хранилище, политика резервирования и
  ключей. LDAP bind администратора в стенде следует заменить учётной записью
  с правом чтения только нужных подразделений каталога.
- Образ OpenLDAP исходного учебного окружения и сборочная цепочка React требуют
  отдельного обновления и проверки уязвимостей перед промышленным использованием.
- Нативные Android/iOS-клиенты, CRM и магазин на диаграмме остаются исходными
  компонентами. Их отдельный код отсутствует в репозитории; реализован React-клиент.
- Для входа через настоящий Яндекс ID нужны зарегистрированное OAuth-приложение,
  его секрет и разрешённый callback. Без них проверяется код, но не внешний вход.
