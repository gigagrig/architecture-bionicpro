# Запуск и проверка системы доступа

## Подготовка

Нужны Docker с Compose v2, Python 3.12+, OpenSSL. Для локальных тестов требуется
виртуальное окружение Python. Node и Maven на хосте не нужны: сборка происходит
в контейнерах.

Общий стенд включает доступ, отчётность, S3/CDN и CDC. Используйте
[единый порядок запуска и проверки готовности](../Task4/operations.md#подготовка-и-запуск).

Первый запуск загружает образы и собирает React, Python-сервис и Java-провайдер.
Скрипт `scripts/prepare-local.py` создаёт `.env` со случайными секретами,
сертификат `.local/tls/localhost.crt`
и приватный ключ. Эти файлы исключены из Git. Повторный запуск их сохраняет.
Секреты администратора и клиента следует смотреть локально в `.env`, не
публиковать в отчёте и не добавлять в репозиторий.

Личный кабинет доступен через HTTPS-порт `127.0.0.1:3443`; служебный интерфейс
Airflow — через `127.0.0.1:8085`. Keycloak, LDAP, базы данных и BFF
не публикуют свои порты на хост. Установленный ранее учебный стенд на 3000/8080
может работать параллельно. Его данные и bind mount `postgres-keycloak-data`
новый проект не использует.

## Сертификат и первый вход

1. Импортируйте `.local/tls/localhost.crt` в доверенные центры сертификации
   браузера для локальной проверки. В Firefox: «Настройки → Приватность и защита →
   Сертификаты → Просмотр сертификатов → Центры сертификации → Импортировать»;
   разрешите идентификацию сайтов. После удаления стенда удалите это доверие.
2. Откройте `https://localhost:3443` и нажмите «Войти».
3. Используйте одну из тестовых записей таблицы ниже.
4. При первом входе Keycloak покажет настройку OTP. В Google Authenticator или
   FreeOTP выберите добавление записи по QR-коду, отсканируйте код, введите
   текущий шестизначный пароль и название устройства.
5. После входа нажмите «Проверить доступ». Затем выйдите и войдите повторно:
   после пароля должен появиться запрос одноразового кода. Неверный код не
   должен предоставлять доступ.

| Источник | Логин | Учебный пароль | Роль |
| --- | --- | --- | --- |
| Keycloak | `user1`, `user2` | `password123` | `user` |
| Keycloak | `prothetic1`, `prothetic2`, `prothetic3` | `prothetic123` | `prothetic_user`, `prosthetic_user` |
| Keycloak | `admin1` | `admin123` | Бизнес-роль `administrator`, не администратор Keycloak |
| LDAP | `john.doe`, `alex.johnson` | `password` | `prothetic_user`, `prosthetic_user` |
| LDAP | `jane.smith` | `password` | `user` |

Это синтетические аккаунты исходного задания. Для эксплуатации их необходимо
удалить. Не добавляйте реальные персональные или медицинские данные в стенд.

Консоль администратора: `https://localhost:3443/identity/admin/`, логин `admin`,
пароль `KEYCLOAK_ADMIN_PASSWORD` из `.env`. В ней выберите `reports-realm`.

## Автоматические проверки

```bash
python3 -m venv .venv
.venv/bin/pip install -r bionicpro-auth/requirements-test.txt
PYTHONPATH=bionicpro-auth .venv/bin/python -m pytest bionicpro-auth/tests/test_security.py -q
BIONICPRO_E2E=1 .venv/bin/python -m pytest bionicpro-auth/tests/test_live.py -q --tb=short
```

Первая команда pytest проверяет серверную логику с подменой внешних сервисов.
Вторая работает с настоящими Keycloak, OpenLDAP и PostgreSQL через HTTPS,
проверяет OTP и обновление токена после ожидания 122 секунд. Она создаёт и
удаляет отдельные временные аккаунты и сбрасывает OTP **только трёх учебных
пользователей LDAP из таблицы**. Не запускайте её против рабочего окружения.
Пароли этих LDAP-пользователей не меняются.

Тестовый клиент проверяет сертификат через `.local/tls/localhost.crt`;
отключать TLS-проверку не требуется. Пока стенд загружается, шлюз может отвечать
502; дождитесь готовности постоянных сервисов по инструкции общего запуска.

В DevTools браузера можно дополнительно проверить:

1. Network: ответы `/auth/session` и `/api/protected` не содержат OAuth-токенов.
2. Application/Storage → Cookies: `__Host-bionicpro-session` имеет `HttpOnly`,
   `Secure`, `SameSite=Lax`, меняет значение после каждого защищённого запроса.
3. После двух минут без перезагрузки страницы «Проверить доступ» продолжает
   работать; запросов браузера к token endpoint Keycloak нет.
4. После выхода `/api/protected` возвращает 401.

## Подключение Яндекс ID

Внешний вход по умолчанию выключен: фиктивные OAuth-реквизиты не подходят для
реального Яндекса. Для включения:

1. В [Яндекс OAuth](https://oauth.yandex.ru/client/new/id/) зарегистрируйте
   приложение для авторизации. Выберите разрешения `login:info`, `login:email`.
   Callback для локального стенда:
   `https://localhost:3443/identity/realms/reports-realm/broker/yandex/endpoint`.
   Если кабинет требует публичный адрес, разверните стенд на доступном HTTPS-домене
   и замените origin, сертификаты, имя сервера и forwarded port в конфигурации
   шлюза; тот же адрес внесите в redirect URI клиента BFF и callback Яндекса.
2. В локальном `.env` задайте `YANDEX_ENABLED=true`, `YANDEX_CLIENT_ID`,
   `YANDEX_CLIENT_SECRET`. Не пересылайте secret в чат и не коммитьте его.
3. Для уже созданного realm примените настройки через Admin API:

   ```bash
   python3 scripts/keycloak-config.py configure-yandex
   docker compose up -d --force-recreate bionicpro-auth
   docker compose restart gateway
   ```

   Импорт при старте не перезаписывает существующий realm. Поэтому одного
   изменения `.env` и перезапуска Keycloak для готовой БД недостаточно.
4. Нажмите «Войти через Яндекс ID», подтвердите доступ в Яндексе, затем настройте
   или введите OTP Keycloak. Внешняя авторизация не отменяет OTP приложения.
5. После входа выберите «Не сейчас». Запись в `yandex_profiles` не должна появиться.
   При следующем входе нажмите «Разрешить»: BFF должен запросить профиль и сохранить
   его в PostgreSQL. Медицинские данные в Яндекс не передаются.
6. Проверьте наличие записи без вывода профиля:

   ```bash
   docker compose exec profile_db psql -U profiles -d profiles -c 'SELECT count(*) FROM yandex_profiles;'
   ```

7. Нажмите «Удалить сохранённый профиль Яндекса» и повторите проверку количества.
   Удаление относится к профилю BionicPRO; разрешение самому Яндексу отзывается
   отдельно в настройках Яндекс ID.

Брокер использует стабильный ID Яндекса; автоматического объединения записей
по email нет. Перед согласием Keycloak уже выполняет запрос к Яндексу для
подтверждения личности, но сохраняет только идентификатор связи. Дополнительный
запрос и сохранение имени/email в БД приложения выполняются после согласия.

## Экспорт и повторное развёртывание

```bash
python3 scripts/keycloak-config.py export
```

Команда получает экспорт настроенного realm через Admin API и записывает
`keycloak/keycloak-results-export.json`. Рабочие секреты заменяются ссылками на
переменные окружения; временные пользователи и OTP-секреты не экспортируются.
Вместо них добавляются исходные синтетические пользователи с обязательной
регистрацией OTP. Поэтому файл подходит для импорта в чистый стенд и не является
резервной копией пользовательских данных.

Остановить стенд без удаления данных: `docker compose down`. Повторный запуск
использует существующие тома. Для отдельной чистой проверки можно задать другое
имя проекта `docker compose -p bionicpro-task1-check ...`, предварительно
остановив основной стенд, чтобы освободить порт 3443. Не удаляйте тома ради
применения конфигурации к работающим пользователям; используйте Admin API.

## Фиксация ручных проверок

Автоматические тесты не подтверждают работу конкретного приложения на вашем
телефоне или реального Яндекс-аккаунта. Выполните разделы
«Сертификат и первый вход» и «Подключение Яндекс ID», затем запишите дату,
использованное приложение и фактический результат в
[раздел ручных проверок report.md](../report.md#ручные-проверки-пользователя).
Скриншоты условием не требуются. Если нужны дополнительные иллюстрации,
создайте `Task1/screenshots/` и сохраните:

- `otp-login.png`: экран запроса OTP при повторном входе после пароля.
- `ldap-role.png`: Keycloak → Users → `john.doe` → Role mapping с эффективной
  ролью `prosthetic_user`.
- `yandex-consent.png`: экран согласия BionicPRO после входа через Яндекс и OTP.
- `yandex-saved.png`: интерфейс с кнопкой удаления сохранённого профиля.

Не снимайте QR-код настройки OTP, секреты, значения cookie или токены.
Места для необязательных ссылок находятся в том же разделе `report.md`.
