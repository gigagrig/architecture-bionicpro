# Общий стенд BionicPRO

Стенд объединяет вход, отчётность, хранение файлов и доставку изменений
источников (CDC). Эти команды относятся к текущему коду репозитория.
Архитектурные документы отдельных решений могут описывать исходные варианты.

## Подготовка и запуск

Команды выполняются из корня репозитория. Нужны Docker с Compose v2,
Python 3.12+, OpenSSL и сеть для загрузки закреплённых образов.
Node и Maven на хосте не нужны: приложения собираются в контейнерах.
Для первого запуска также нужна сборка MinIO; она требует нескольких минут
и свободного места.

```bash
python3 scripts/prepare-local.py
docker compose build minio
docker compose build minio-init
docker compose build reports-api bionicpro-auth frontend keycloak \
  airflow-init airflow-scheduler airflow-webserver reports-seed
docker compose up -d
docker compose up -d --no-deps --wait --wait-timeout 240 \
  airflow-scheduler airflow-webserver cdn reports-api gateway
docker compose ps -a
docker compose logs debezium-init cdc-schema crm-cdc-init telemetry-cdc-init
```

Скрипт `scripts/prepare-local.py` создаёт `.env` со случайными секретами,
сертификат `.local/tls/localhost.crt` и приватный ключ. Эти файлы исключены
из Git; повторная подготовка их сохраняет. Секреты смотрите локально в `.env`,
не публикуйте в отчёте и не добавляйте в репозиторий.

При обновлении стенда первые две сборки MinIO можно пропустить,
если образы уже существуют. Подготовка сохраняет прежние секреты и добавляет
`CRM_CDC_PASSWORD` и `TELEMETRY_CDC_PASSWORD`. Compose сохраняет все старые
тома и имя проекта; новый том `kafka-data` хранит сообщения и позиции Connect.
Не удаляйте тома для применения миграций.

`crm-cdc-init` добавляет ключ владения, ограниченный аккаунт и публикацию;
`telemetry-cdc-init` настраивает второй источник. `kafka-init` создаёт топики,
`cdc-schema` применяет SQL, `debezium-init` регистрирует коннекторы. Все пять
одноразовых сервисов должны закончить с кодом 0. Сервис Connect должен быть
`healthy`; дополнительно проверьте задачи коннекторов:

```bash
docker compose exec kafka-connect curl -fsS http://localhost:8083/connectors/bionicpro-crm/status
docker compose exec kafka-connect curl -fsS http://localhost:8083/connectors/bionicpro-telemetry/status
```

Ожидается `RUNNING` и у коннектора, и у задачи. Это ещё не доказывает завершение
начального снимка; готовность определяется по данным внутри ClickHouse.

Стенд: `https://localhost:3443`; Airflow: `http://localhost:8085`.
Пароль администратора Airflow хранится в локальном `.env`. Keycloak, LDAP,
базы и BFF не публикуют порты на хост. Прежний учебный стенд на 3000/8080
может работать параллельно; его данные и `postgres-keycloak-data` не используются.
Учебные аккаунты `user1`/`user2`, пароль `password123`, затем одноразовый
код. Доверие сертификату и настройка OTP описаны в
[руководстве по входу](Task1/authentication.md#сертификат-и-первый-вход).
OTP — одноразовый код из приложения-аутентификатора.

## Демоданные и публикация периода

```bash
docker compose --profile tools run --rm reports-seed --days 3
docker compose exec -T clickhouse sh -c \
  'clickhouse-client --user etl --password "$CLICKHOUSE_PASSWORD" --query "SELECT * FROM reporting.cdc_readiness"'
```

После доставки CDC ожидаются `checkpoints=2`, `live_sources=2` и
`closed_through`, покрывающий нужный период. Подождите примерно 10–30 секунд;
время зависит от ресурсов и объёма начального снимка.

Задача `publish_cdc` DAG `bionicpro_reports` запускается каждую минуту.
Она автоматически добавляет вчерашний день UTC и обновляет ранее опубликованные
дни, если изменились показатели. Чтобы опубликовать три дня из вывода заполнения,
отправьте по одному запуску на каждый день:

```bash
docker compose exec airflow-scheduler airflow dags trigger bionicpro_reports --conf '{"day":"2026-09-29"}'
docker compose exec airflow-scheduler airflow dags trigger bionicpro_reports --conf '{"day":"2026-09-30"}'
docker compose exec airflow-scheduler airflow dags trigger bionicpro_reports --conf '{"day":"2026-10-01"}'
```

Пример соответствует запуску 2 октября 2026 года. Замените даты на фактические
завершённые дни. Scheduler выполняет запуски последовательно. В Airflow Grid
проверьте `success` у `publish_cdc`; задача включает запись витрины, проверку
числа строк и обновление S3-каталога. Явный `day` создаёт новую версию даже при
неизменных данных; обычный минутный запуск сохраняет версии без изменений.

В браузере получите отчёт от первого дня до дня после последнего, например
`2026-09-29` → `2026-10-02`. Конечная дата не включается. У `user1` видны его
два протеза, у `user2` — только его протез. Неподготовленный день даёт `409`.
API использует `catalog/cdc-current.json`; каталог старого ETL не требуется
копировать в новый, поскольку UUID версий и исходная витрина различаются.

## Остановка и повторный запуск

`docker compose down` останавливает стенд без удаления данных. Повторный запуск
использует существующие тома. Для отдельной чистой проверки можно задать имя
проекта `docker compose -p bionicpro-task1-check ...`, предварительно остановив
основной стенд, чтобы освободить порты 3443 и 8085. Не удаляйте тома ради
применения конфигурации к работающим пользователям; используйте миграции
и Admin API Keycloak.

## Получение и скачивание

1. Войдите в личный кабинет как `user1`.
2. Выберите начальную дату и конечную дату, **не включаемую** в отчёт.
   Для данных 29 сентября — 1 октября укажите `2026-09-29` и `2026-10-02`.
3. Нажмите «Получить отчёт». Таблица покажет только два протеза `user1`.
   У запасного протеза будут нули, отклик и заряд — «—».
4. Нажмите «Скачать отчёт JSON». Загружается актуальная версия через CDN;
   если витрина обновилась после показа таблицы, скачанный файл отражает новые данные.
5. Выйдите и войдите как `user2`: будет доступен только его протез.
6. Запросите день, который не опубликован Airflow. Интерфейс покажет
   сообщение с отсутствующими днями; частичный отчёт не формируется.

API использует `GET /api/reports?from=YYYY-MM-DD&to=YYYY-MM-DD`.
`GET /reports` на том же HTTPS-адресе — равнозначный публичный маршрут через BFF.
Оба требуют cookie серверной сессии. Передавать токены в браузере не нужно.
Параметры `user_id`, `subject` и любые другие, кроме `from`/`to`, запрещены.
Повторяющиеся параметры также отклоняются. Максимальный период — 31 день UTC.

## Ручная проверка интерфейса

После добавления локального сертификата в доверенные откройте Chrome/Firefox,
перейдите на основной адрес и выполните шаги получения отчёта выше.
Проверьте читаемость таблицы, скачивание JSON, сообщение о недоступном дне
и отсутствие данных `user1` при входе `user2`.

## Автоматические проверки

Команды выполняются из корня репозитория. Для Go нужны Go 1.22+ и доступ
к загрузке закреплённой зависимости. Python-проверки используют локальное
виртуальное окружение; проверки Airflow выполняются в контейнере.

### Подготовка окружения Python

```bash
python3 -m venv .venv
.venv/bin/pip install -r bionicpro-auth/requirements-test.txt
```

### Проверки Go и серверной логики

```bash
cd reports-api
go test -race ./...
go vet ./...
cd ..
PYTHONPATH=bionicpro-auth .venv/bin/python -m pytest \
  bionicpro-auth/tests/test_security.py bionicpro-auth/tests/test_reports.py -q
```

Python-тесты этой группы подменяют внешние сервисы.

### Публикация витрины

```bash
docker compose exec -e PYTHONPATH=/opt/airflow/dags airflow-scheduler \
  python -m pytest /opt/airflow/tests/test_etl.py -q -p no:cacheprovider
```

### Сквозная проверка отчётности

Запустите стенд и дождитесь готовности сервисов. Нужен доступ к Docker;
HTTPS проверяется через `.local/tls/localhost.crt`, отключать проверку не нужно.

```bash
BIONICPRO_E2E=1 PYTHONPATH=bionicpro-auth .venv/bin/python -m pytest \
  Task2/tests/test_reports_live.py -q
```

Тест создаёт временные аккаунты и синтетические события, выполняет настоящий
DAG и проверяет свои/чужие данные и пропуски периода. Затем удаляет аккаунты
и записи источников. Неизменные версии витрины и S3-файлы временных аккаунтов
остаются до очистки истории.

Во время сквозных тестов не запускайте ручную публикацию и не получайте
другие отчёты: это меняет версии и общий счётчик запросов API. Для обычной
публикации используйте `dags trigger`; внутренний `dags test` может обходить
ограничения планировщика и требует отсутствия другого издателя.
